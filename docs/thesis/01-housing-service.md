# خدمة إدارة السكن — HousingService

> الخدمة المحورية في المنصة. تدير دورة حياة التسكين كاملةً: من فتح دورة القبول، مرورًا بتقديم الطالب لطلبه ومراجعة وثائقه، ثم قرار القبول، وتكوين غروبات السُّكن، فالتخصيص الفعلي لغرفة، ودفع الرسوم، وانتهاءً بإخلاء المبنى في نهاية العام.

---

## 1. نظرة عامة

### 1.1 الغرض

أتمتة العمل الإداري لقسم السكن في المدينة الجامعية، مع الحفاظ على **سيطرة الموظّف الإداري اليدوية** على القرارات الجوهرية (المراجعة، القبول، التخصيص، الإخلاء) — فالنظام يوفّر البيانات والتصفية والتحقق من القيود، بينما القرار النهائي بشرياً. لا يوجد في النظام أي خوارزمية ترشيح/تسجيل نقاط آلية.

### 1.2 الموقع في المعمارية

| الخاصية | القيمة |
|---|---|
| التقنية | ASP.NET Core (.NET 9)، EF Core، SQL Server |
| المنفذ المحلي | `5054` (خلف البوابة `5067`) |
| قاعدة البيانات | `HousingServiceDb` (مستقلة) |
| المسارات الجذرية | `/api/buildings`، `/api/housing-cycles`، `/api/governorates`، `/api/housing-requests`، `/api/housing-groups`، `/api/allocations` |
| الاعتماديات الخارجية | AuthService (بحث أسماء المستخدمين + المحفظة)، NotificationService (الإشعارات)، Cloudinary (تخزين الوثائق) |
| المهام الخلفية | `PaymentReminderJob` — مؤقّت دوري كل 24 ساعة لتذكير الطلاب بموعد دفع الرسوم |
| اختبارات آلية | `HousingService.Tests` (xUnit، قاعدة بيانات EF InMemory معزولة لكل اختبار) — ~59 اختبارًا |

### 1.3 نطاق مقصود (قرارات تبسيط)

استُبعدت عن قصد مفاهيم واردة في التصميم الأولي للأطروحة، لعدم وجود حالة استخدام واضحة أو لتبسيط النموذج:

- **لا مستويات جودة/تسعير للغرف (Tier):** كل الغرف مستوى واحد ورسم واحد ثابت.
- **لا تسجيل نقاط قبول آلي:** المراجعة والقبول قرار إداري بحت.
- **لا تصفّح للطالب للغرف ولا «مفضّلة»:** الطالب لا يختار غرفة إطلاقًا؛ يقدّم بياناته فقط، والتخصيص لاحقًا بيد الإدارة.
- **لا حذف للمباني أو الغرف:** كلاهما كيان فيزيائي واقعي؛ إخراجه من الخدمة تغييرٌ في `Status` (صيانة/مغلق) لا حذفٌ فعلي.
- **الفصل الجندري على مستوى المبنى كاملًا** لا على مستوى الغرفة.
- **سعة الغرفة موحّدة داخل المبنى** (`Building.StandardRoomCapacity`) لا لكل غرفة، تفاديًا لتضارب البيانات.

## 2. النموذج البرمجي وعلاقات الجداول

### 2.1 الكيانات (الجداول)

| الجدول | الوصف | المفتاح |
|---|---|---|
| `Buildings` | مبنى سكني: اسم، جنس المبنى، حالة، عدد طوابق، سعة الغرفة القياسية | `Id` (int) |
| `Rooms` | غرفة داخل مبنى: رقم الغرفة، الطابق، الحالة | `Id` (int) |
| `HousingCycles` | دورة تسكين سنوية (مثلاً «2026‑2027»): اسم، حالة (مفتوحة/مغلقة) | `Id` (int) |
| `Governorates` | جدول مرجعي للمحافظات المخدومة (مُدار من الإدارة) | `Id` (int) |
| `HousingRequests` | طلب تسكين لطالب ضمن دورة: بيانات شخصية + سكنية + حالة + حقول الدفع | `Id` (int) |
| `HousingRequestDocuments` | وثيقة مرفقة بالطلب: النوع، المسار (Cloudinary URL)، حالة المراجعة | `Id` (int) |
| `HousingGroups` | غروب سُكن (رفقاء غرفة) ضمن دورة: قائد، رمز فريد، حالة، حد أقصى للأعضاء | `Id` (int) |
| `GroupInvitations` | طلب انضمام لغروب (سحب فقط): الطالب، الحالة، تواريخ | `Id` (int) |
| `AdmissionDecisions` | قرار قبول لطلب واحد (علاقة 1:1): الحالة، السبب، المُراجِع، التاريخ | `Id` (int) |
| `Allocations` | تخصيص فيزيائي لغرفة: طلب فردي **أو** غروب + غرفة + تاريخ التخصيص + تاريخ الإخلاء | `Id` (int) |
| `HousingSettings` | سطر إعداد وحيد (Id=1): مهلة الدفع، أيام التذكير المسبق، مبلغ الرسم | `Id` = 1 |

### 2.2 حقول الكيانات الرئيسية

**Building:** `Name` (فريد)، `Gender` {Male, Female, Mixed(احتياطي)}، `Status` {Active, Inactive, Maintenance, Full}، `FloorsCount`، `StandardRoomCapacity`، `Description`.

**Room:** `BuildingId` (FK)، `RoomNumber` (فريد ضمن المبنى)، `Floor`، `Status` {Available, Occupied, Full, Maintenance, Closed}. (`CurrentOccupancy` عمود موجود لكنه **لا يُعتمد عليه أبدًا** — الإشغال يُحسب حيًّا من `Allocations`.)

**HousingRequest:**
- هوية ودورة: `StudentId` (من AuthService)، `HousingCycleId` (FK)، `GovernorateId` (FK).
- بيانات: `Gender` (مُصرّح ذاتيًا — لازم محليًا لقاعدة تطابق جنس الغروب)، `AcademicLevel` {First..Fifth}، `DetailedAddress`، `HasSpecialNeeds`، `SpecialNotes`.
- ساكن سابق: `IsPreviousResident`، `PreviousBuildingId` (FK)، `PreviousFloor`، `PreviousRoomNumber`.
- ربط: `HousingGroupId` (FK، nullable).
- حالة: `Status` {Submitted, NeedsRevision, Locked}، `SubmittedAt`، `LockedAt`.
- الدفع: `PaymentDueDate` (nullable)، `IsPaid`، `PaidAt`، `ReminderSent`.
- فهرس فريد: `(StudentId, HousingCycleId)` — طلب واحد لكل طالب لكل دورة.

**HousingGroup:** `LeaderId`، `Code` (فريد، صيغة `GRP-{السنة}-{4 رموز}`)، `HousingCycleId` (FK)، `Status` {Open, Locked, Allocated, Closed}، `MaxMembers` = 4.

**GroupInvitation:** `HousingGroupId` (FK)، `InvitedStudentId` = `InvitedByStudentId` (انضمام ذاتي)، `Status` {Pending, Accepted, Rejected, Cancelled}. فهرس فريد **جزئي**: `(HousingGroupId, InvitedStudentId)` عندما `Status = Pending` فقط — كي يُسمح بإعادة طلب الانضمام بعد رفض سابق (كل محاولة سطر مستقل، حفاظًا على السجل).

**AdmissionDecision:** `HousingRequestId` (FK، 1:1)، `Status` {Pending, Accepted, WaitingList, Rejected}، `DecisionReason`، `ReviewedBy`، `DecisionDate`.

**Allocation:** `HousingRequestId` (nullable) **XOR** `HousingGroupId` (nullable، فهرس فريد حيث ليس NULL — غروب واحد لا يملك إلا تخصيصًا واحدًا مدى الحياة)، `RoomId` (FK)، `AllocatedAt`، `VacatedAt` (nullable — «تخصيص نشط» يعني `VacatedAt == null`).

### 2.3 مخطط العلاقات (ERD وصفي)

```
HousingCycle 1───∞ HousingRequest ∞───1 Governorate
                     │  │  │
                     │  │  └──1:1── AdmissionDecision           (Cascade عند حذف الطلب)
                     │  └────1:∞── HousingRequestDocument       (Cascade)
                     │
        HousingGroup 1───∞ HousingRequest   (Members؛ FK = HousingGroupId، SetNull)
             │  │
             │  └───1:∞── GroupInvitation                       (Cascade)
             │  └───1:1─── Allocation        (FK = HousingGroupId، SetNull، فريد)
             │
HousingCycle 1───∞ HousingGroup

Building 1───∞ Room 1───∞ Allocation                            (Room→Allocation: Restrict)
Building 1───∞ HousingRequest (PreviousBuilding، Restrict)

HousingRequest 1───∞ Allocation   (FK = HousingRequestId، SetNull)
HousingSettings: سطر مفرد مستقل (Id = 1)
```

**سلوك الحذف (Delete Behavior) المقصود:**
- حذف `HousingRequest` ⇐ يُشلّل (Cascade) وثائقه وقراره؛ ويُفرِّغ (SetNull) `Allocation.HousingRequestId`. لذلك يمنع النظام حذف طلبٍ له تخصيص نشط (تفاديًا لسطر تخصيص «يتيم» يُبقي الغرفة مشغولة بلا ساكن معروف).
- خروج عضو من غروب ⇒ `HousingRequest.HousingGroupId = null` (SetNull) لا حذف الطلب.
- لا حذف للمباني/الغرف بتاتًا (لا توجد نقاط نهاية حذف).
- الإخلاء لا يحذف `Allocation` بل يختم `VacatedAt` (حفظ السجل التاريخي: من سكن أين ومتى).

### 2.4 البيانات الأولية (Seed)

عبر ترحيلة `SeedBuildingsAndRooms` تُحقَن محاكاة للمدينة الجامعية في جامعة حلب:
- **20 مبنى** (`Id` = 1..20)؛ المباني 1–10 إناث، 11–20 ذكور.
- كل مبنى **6 طوابق × 44 غرفة** = 264 غرفة، بترقيم `{الطابق}{01..44}` (مثلاً 101..144، 201..244...).
- `StandardRoomCapacity` = 4 لكل المباني ⇒ إجمالي 5280 غرفة.
- محافظة أولية: «حلب» (`Id` = 1).
- `HousingSettings` الأولي: `PaymentDeadlineDays` = 15، `ReminderDaysBefore` = 3، `HousingFeeAmount` = 0.

## 3. قواعد العمل (Business Rules)

### 3.1 دورة التسكين (HousingCycle)

| # | القاعدة |
|---|---|
| BR‑C1 | يجوز أن تكون **دورة واحدة فقط «مفتوحة»** في أي لحظة؛ محاولة فتح ثانية ترفض حتى تُغلق الأولى. |
| BR‑C2 | الدورة قابلة لإعادة الفتح بحرّية (مبدّل Open/Closed بسيط، ليس آلة حالة أحادية الاتجاه). المبرّر: إذا لم يُثبِّت طلابٌ مقبولون أماكنهم (لم يدفعوا) يُعيد الإداري فتح الدورة لقبول آخرين في الأماكن المتحرّرة. |
| BR‑C3 | الطالب لا يختار الدورة؛ النظام يحلّ «الدورة المفتوحة الحالية» تلقائيًا عند تقديم أي طلب أو إنشاء غروب. |
| BR‑C4 | فتح الدورة يفتح باب التقديم للجميع دفعةً واحدة (لا تدريج حسب الكلية). تدرُّج القبول ينشأ طبيعيًا من كون المراجعة يدوية. |
| BR‑C5 | لا يخزّن النظام تاريخ نهاية للدورة؛ الإخلاء حدثٌ إداري لكل مبنى على حدة. |

### 3.2 المباني والغرف

| # | القاعدة |
|---|---|
| BR‑B1 | اسم المبنى فريد؛ `StandardRoomCapacity` يجب أن تكون > 0. |
| BR‑B2 | الفصل الجندري على مستوى المبنى كاملًا. |
| BR‑B3 | رقم الغرفة فريد ضمن المبنى الواحد. |
| BR‑B4 | **لا يجوز** تعديل حالة المبنى إلى `Inactive` / `Maintenance` عبر التعديل العادي إن كان فيه ساكنون نشطون؛ يجب المرور بمسار الإخلاء المخصّص أولًا. |
| BR‑B5 | **لا يجوز** تعديل حالة الغرفة يدويًا بما يناقض الإشغال الفعلي: غرفة مشغولة لا تُقبل إلا `Occupied`/`Full`؛ غرفة فارغة لا تُقبل `Occupied`/`Full`. لإفراغ غرفة يجب استخدام نقاط التخصيص (إخلاء/نقل) لا تعديل الحالة. |
| BR‑B6 | إشغال الغرفة يُحسب دائمًا حيًّا من `Allocations` النشطة (`VacatedAt == null`): فردي = 1، غروب = عدد أعضائه. عمود `Room.CurrentOccupancy` لا يُعتمد. |

### 3.3 طلب التسكين (HousingRequest)

| # | القاعدة |
|---|---|
| BR‑R1 | يُقبل الطلب من دور `student` فقط، وضمن **دورة مفتوحة** فقط. |
| BR‑R2 | **طلب واحد لكل طالب لكل دورة** (مفروض بفهرس فريد على مستوى قاعدة البيانات، لا على مستوى التطبيق فقط). |
| BR‑R3 | التقديم عملية **واحدة** مع كل الوثائق الخمس الإلزامية: صورة شخصية، وجها الهوية الوطنية، وجها الهوية الجامعية. لا يمكن التقديم بدونها. |
| BR‑R4 | وثيقتان اختياريتان (وصل مغادرة، سند إقامة) يجوز إرفاقهما لاحقًا أو أن يطلبهما الإداري عبر إشعار. |
| BR‑R5 | إذا كان الطالب ساكنًا سابقًا وجب تحديد `PreviousBuildingId` (ويُتحقّق من وجوده). |
| BR‑R6 | الطالب يعدّل طلبه ما دام غير `Locked` (أي `Submitted` أو `NeedsRevision`). أي تعديل يُعيد الحالة إلى `Submitted` ويُعيد الطلب إلى طابور المراجعة. |
| BR‑R7 | إعادة رفع وثيقة عند التعديل تستبدل ملف Cloudinary القديم وتُعيد حالة مراجعتها إلى `Pending`. |
| BR‑R8 | لا يجوز تغيير `Gender` أثناء العضوية في غروب (يجب مغادرة الغروب أولًا). |
| BR‑R9 | حذف الطلب: متاح للطالب لطلبه، وللإداري لأي طلب. يُمنع إن وُجد تخصيص نشط (فردي أو عبر غروبه). الحذف يشمل: إخراج الطالب من غروبه، وإلغاء طلبات انضمامه المعلّقة لغروبات أخرى، وحذف ملفات Cloudinary، وإشعار الطالب إن حذفه إداري. |

### 3.4 مراجعة الوثائق والقرار (AdmissionDecision)

| # | القاعدة |
|---|---|
| BR‑D1 | رفض أي وثيقة يقلب حالة **الطلب كله** إلى `NeedsRevision` ويُطلق إشعارًا للطالب بالتصحيح. |
| BR‑D2 | لا يمكن تسجيل قرار قبول بينما الطلب `NeedsRevision` — يجب حسم الوثيقة المُعلَّمة أولًا. |
| BR‑D3 | القرار قيمته إحدى: `Accepted` / `Rejected` / `WaitingList` (ليس `Pending`). |
| BR‑D4 | القرار **عملية Upsert**: استدعاؤه ثانيةً على طلب له قرار يُحدِّثه في مكانه (مثال: ترقية من `WaitingList` إلى `Accepted` لاحقًا). |
| BR‑D5 | **أول قرار** يقلب `HousingRequest.Status` إلى `Locked` ويختم `LockedAt`؛ القرارات اللاحقة لا تُعيد القفل. |
| BR‑D6 | عند `Accepted` أو `Rejected` تُحسم تلقائيًا كل الوثائق التي بقيت `Pending` (لأن الإداري لا يقرّر دون حكمٍ ضمني على الوثائق). |
| BR‑D7 | إذا صار قرار عضو غروب `Rejected` أو `WaitingList` يُستبعَد ضمنيًا من غروبه (يُعاد استخدام روتين الإزالة المشترك الذي يُزامن حالة الغرفة أيضًا). |
| BR‑D8 | إذا انعكس قرار طالب **فردي** من `Accepted` إلى `Rejected`/`WaitingList` ولديه تخصيص نشط، يُفرَّغ تخصيصه تلقائيًا (يُعاد استخدام منطق الإخلاء). |
| BR‑D9 | كل قرار (أول أو معدَّل) يُطلق إشعارًا للطالب بصيغة مناسبة للحالة. |

### 3.5 غروبات السُّكن (HousingGroup)

| # | القاعدة |
|---|---|
| BR‑G1 | القائد ينشئ الغروب؛ الحد الأقصى 4 (القائد + 3). |
| BR‑G2 | كل عضو (والقائد) يجب أن يملك **طلب تسكين للدورة الحالية** قبل الانضمام — الغروب يربط طلبات قائمة لا يبدأ مسار تقديم مستقلًا. |
| BR‑G3 | الطالب في **غروب نشط واحد فقط** (قائدًا أو عضوًا) في الدورة الواحدة. |
| BR‑G4 | لكل غروب `Code` فريد. الانضمام **سحب فقط**: الطالب يُدخل الرمز فيُنشأ طلب انضمام `Pending` يوافق عليه القائد صراحةً (لا انضمام تلقائي، ولا دعوة يرسلها القائد). |
| BR‑G5 | يُرفض الانضمام إن: الغروب ليس `Open`، أو الطالب مجمَّع أصلًا، أو طلبه مرفوض، أو **جنسه لا يطابق جنس القائد** (يُتحقَّق عند الانضمام لا يؤجَّل)، أو تجاوزت السعة (تُحسب الطلبات المعلَّقة أيضًا كي لا تُفرَط الأماكن قبل الموافقة). |
| BR‑G6 | عند الموافقة على العضو الأخير (بلوغ `MaxMembers`) يقلب الغروب إلى `Locked` تلقائيًا وتُلغى بقية طلبات الانضمام المعلّقة. |
| BR‑G7 | إذا كان الغروب **مسكَّنًا أصلًا** ووافق القائد على عضو جديد، يُتحقَّق من سعة الغرفة المتبقية، وتُحدَّث حالة الغرفة (+1)، ويُشعَر العضو الجديد بغرفته. |
| BR‑G8 | مغادرة/إزالة عضو: إن كان قائدًا تنتقل القيادة لأقدم عضو مقبول متبقٍّ، أو يُحذَف الغروب إن كان آخر عضو. إن غادر عضو عادي من غروب `Locked` يعود إلى `Open`. |
| BR‑G9 | كل مسارات مغادرة العضو (مغادرة ذاتية، إزالة من الإداري، إزالة من القائد، انعكاس قرار، حذف طلب) تمرّ عبر **روتين واحد مشترك** يُزامن حالة الغرفة/التخصيص ويُشعِر بقية الأعضاء (ومن أصبح قائدًا). |
| BR‑G10 | تكوين الغروب يتطلّب طلبًا **مُقدَّمًا** فقط (أي حالة عدا `NeedsRevision` عمليًا)؛ لا يتطلّب `Accepted` — لأن الغروبات تُشكَّل خلال نافذة التقديم قبل صدور القرارات. |

### 3.6 التخصيص (Allocation)

| # | القاعدة |
|---|---|
| BR‑A1 | التخصيص منفصل عن القبول: القبول يجيب «هل يستحق سكنًا؟»، التخصيص يجيب «في أي غرفة؟» — بينهما فجوة زمنية محتملة. |
| BR‑A2 | قيود صلبة لا تُنتهَك أبدًا: **تطابق الجنس** بين الطالب/الغروب والمبنى، و**سعة كافية** في الغرفة. |
| BR‑A3 | لا خوارزمية ترشيح: النظام يُصفّي كل الغرف في المنظومة إلى مرشّحات صالحة (جنس + سعة + حالة `Available`/`Occupied`)، والإداري يختار يدويًا. |
| BR‑A4 | التخصيص الفردي يتطلّب: أن الطلب ليس ضمن غروب، وقراره `Accepted`، ولا تخصيص قائم له. |
| BR‑A5 | تخصيص الغروب يتطلّب: **كل عضو حالي مقبول فرديًا** (هكذا يُحسم «القبول الجزئي» — يجب على الإداري حسم/إزالة كل عضو أولًا)، ولا تخصيص قائم للغروب. |
| BR‑A6 | كل القواعد تُعاد التحقق منها لحظة الالتزام (Commit) لا اعتمادًا على قائمة المرشّحات السابقة (تفاديًا لتسابق إداريَّين). |
| BR‑A7 | للغروب **تخصيص واحد مشترك** (غرفة واحدة للجميع)؛ وضع الغروب يتقدّم على أي تفضيل فردي «أعيدوني لغرفتي القديمة» (بيانات الغرفة القديمة معروضة كمرجع فقط). |
| BR‑A8 | عند نجاح التخصيص: يُنشأ سطر `Allocation`، وتُحدَّث حالة الغرفة (`Occupied`/`Full`) من الإشغال المحسوب، ويصبح الغروب `Allocated` مع ختم `AllocatedAt`، ويُشعَر كل المتأثرين. |
| BR‑A9 | إدارة ما بعد التخصيص (كلها للإداري): **نقل** (`transfer` — تحديث `RoomId` في مكانه لأن للغروب تخصيصًا فريدًا واحدًا)، **إخلاء تخصيص** (`vacate` — ختم `VacatedAt`)، **إزالة عضو غروب واحد** مع بقاء الباقين، ونسخ «مركزية الطالب» تحلّ التخصيص من معرّف الطالب مباشرةً. |
| BR‑A10 | نقل طالب مجمَّع «وحده» (وله رفاق باقون) = فصله في تخصيص **فردي جديد** بمعرّف جديد، مع بقاء غروبه في الغرفة القديمة. |
| BR‑A11 | كل عمليات ما بعد التخصيص تُعيد حساب حالة الغرفتين القديمة والجديدة قبل التعديل (حساب عددي) وتُشعِر المتأثرين. |

### 3.7 الإخلاء (Building Evacuation)

| # | القاعدة |
|---|---|
| BR‑E1 | الإخلاء لكل مبنى على حدة، بقرار إداري يدوي، غير متزامن بين المباني، وغير مجدول مسبقًا. |
| BR‑E2 | المبنى يُفرَّغ **كليًا** (الكل أو لا شيء لهذا المبنى). |
| BR‑E3 | العملية جزءان: (1) `announce` — إشعار سكّان المبنى فقط (لا بثّ عام)، بلا أي كتابة في قاعدة البيانات، قابل للتكرار. (2) `execute` — ختم `VacatedAt` لكل تخصيص نشط في المبنى، وإرجاع الغرف `Occupied`/`Full` إلى `Available` (دون مسّ `Maintenance`/`Closed`)، وإشعار بالإتمام. |
| BR‑E4 | كلا الجزأين آمن للاستدعاء على مبنى فارغ (يُشعِر/يُفرِّغ صفرًا، ليس خطأً). |
| BR‑E5 | الإخلاء لا يحذف `Allocation` بل يختمه (حفظ السجل التاريخي). كل موضع يحسب إشغالًا أو يتحقّق من «هل يوجد تخصيص» يُصفّي على `VacatedAt == null`. |

### 3.8 الرسوم والدفع (Payment)

| # | القاعدة |
|---|---|
| BR‑P1 | الرسم يُستحقّ فقط بعد **قبول** الطلب. `PaymentDueDate` يُختم **مرّة واحدة** أول مرة يصير القرار `Accepted`، إلى `تاريخ_القبول + PaymentDeadlineDays`، ولا يُحرَّك أبدًا (تغيير الإعداد لاحقًا، أو عكس القرار ثم إعادة قبوله، يُبقي التاريخ الأصلي). |
| BR‑P2 | مبلغ الرسم = `HousingSettings.HousingFeeAmount` واحد عام قابل لتعديل الإدارة (كل الغرف مستوى واحد). يجب أن يكون > 0 كي ينجح الدفع. |
| BR‑P3 | الدفع مبادرة من الطالب: خصم من محفظته في AuthService (`POST /api/internal/wallet/charge`، المرجع `housing-request-{id}`). عند نجاح HTTP 200 فقط يُوسَم `IsPaid` ويُختم `PaidAt` ويُطلَق إشعار إتمام. |
| BR‑P4 | حرّاس الدفع: الطلب موجود، والمستدعي مالكه، وغير مدفوع، وقراره `Accepted`، والرسم مضبوط. رصيد غير كافٍ ⇒ 402 والطلب يبقى غير مدفوع. تعذُّر البوابة (AuthService غير متاح/‏5xx) ⇒ 502 والطلب غير مدفوع. |
| BR‑P5 | حارس الدفع المزدوج هو فحص `IsPaid` (تسابق ضيّق جدًا ما يزال ممكنًا نظريًا — مقبول حاليًا). |
| BR‑P6 | الدفع بعد انقضاء المهلة ما يزال مسموحًا — المهلة تُحرّك التذكير فقط؛ تحرير مكان غير مدفوع إجراء إداري يدوي منفصل. |
| BR‑P7 | `PaymentReminderJob` (BackgroundService) يعمل كل 24 ساعة عبر `IPaymentReminderService.RunAsync()`: يُشعِر كل طلب `Accepted` + غير مدفوع + `!ReminderSent` استحقاقه ضمن `ReminderDaysBefore` يومًا (المتأخّرون مشمولون كي لا تُتخطّى تذكيرات عند فوات دورة)، ثم يضبط `ReminderSent`. |
| BR‑P8 | تحقّق الإعدادات: `PaymentDeadlineDays > 0`، `0 < ReminderDaysBefore < PaymentDeadlineDays`، `HousingFeeAmount >= 0`. |

## 4. حالات الاستخدام (Use Cases)

### UC‑01 فتح دورة تسكين
- **الفاعل:** الإداري.
- **شرط مسبق:** لا توجد دورة مفتوحة أخرى.
- **المسار:** إنشاء دورة (`POST /api/housing-cycles`) بحالة `Closed` ← فتحها (`POST /api/housing-cycles/{id}/open`).
- **ما بعد:** الدورة `Open`؛ يمكن للطلاب التقديم.
- **استثناء:** وجود دورة مفتوحة ⇒ 400 «أغلقها أولًا».

### UC‑02 تقديم طلب تسكين
- **الفاعل:** الطالب.
- **شرط مسبق:** دورة مفتوحة؛ لا طلب سابق للطالب في هذه الدورة؛ توفّر الوثائق الخمس.
- **المسار:** `POST /api/housing-requests` (multipart) بالبيانات + 5 وثائق (+ اختياريتان) ← رفعها إلى Cloudinary ← إنشاء الطلب بحالة `Submitted` وإعادة `RequestId`.
- **ما بعد:** طلب `Submitted` في طابور المراجعة.
- **استثناءات:** لا دورة مفتوحة / طلب مكرّر / نقص وثيقة / `PreviousBuildingId` غير موجود ⇒ 400.

### UC‑03 مراجعة وثيقة ورفضها
- **الفاعل:** الإداري.
- **المسار:** `POST /api/housing-requests/{id}/documents/{documentId}/review` بـ `{Approve, ReviewNotes}`.
- **ما بعد (رفض):** الوثيقة `Rejected`، الطلب `NeedsRevision`، إشعار للطالب.
- **استثناء:** الطلب `Locked` ⇒ 400.

### UC‑04 تصحيح الطالب لطلبه
- **الفاعل:** الطالب.
- **شرط مسبق:** الطلب `Submitted` أو `NeedsRevision` (غير `Locked`).
- **المسار:** `PUT /api/housing-requests/mine/{id}` بالبيانات و/أو إعادة رفع وثيقة ← الحالة تعود `Submitted`.
- **استثناء:** الطلب `Locked` ⇒ 400؛ تغيير الجنس وهو في غروب ⇒ 400.

### UC‑05 قرار القبول
- **الفاعل:** الإداري.
- **شرط مسبق:** الطلب ليس `NeedsRevision`.
- **المسار:** `POST /api/housing-requests/{id}/decision` بـ `{Status, DecisionReason}` ← Upsert للقرار ← أول قرار يقفل الطلب ويختم `LockedAt` ← حسم الوثائق المعلّقة ← ختم `PaymentDueDate` عند أول `Accepted` ← تعاقبات الغروب/التخصيص عند `Rejected`/`WaitingList` ← إشعار الطالب.
- **ما بعد:** `AdmissionDecision` بالحالة المطلوبة؛ الطلب `Locked`.

### UC‑06 إنشاء غروب سُكن
- **الفاعل:** الطالب (يصبح القائد).
- **شرط مسبق:** دورة مفتوحة؛ للطالب طلب في هذه الدورة؛ غير مجمَّع؛ طلبه غير مرفوض.
- **المسار:** `POST /api/housing-groups` ← توليد `Code` فريد ← الغروب `Open` والقائد عضوه الأول.

### UC‑07 طلب انضمام لغروب والموافقة عليه
- **الفاعلون:** طالب راغب + قائد الغروب.
- **المسار:** الراغب `POST /api/housing-groups/join` بالرمز ← تحقّق (`Open`، طلب موجود، غير مجمَّع، غير مرفوض، تطابق الجنس، سعة) ← `GroupInvitation` `Pending` + إشعار للقائد ← القائد `POST /api/housing-groups/invitations/{id}/respond` بـ `{Approve}` ← ربط `HousingRequest.HousingGroupId` ← عند الامتلاء يقفل الغروب ويُلغي الباقي ← (إن مسكَّن: تحقّق سعة + تحديث الغرفة + إشعار غرفة).
- **استثناءات:** رمز خاطئ ⇒ 404؛ خرق أي قاعدة انضمام ⇒ 400.

### UC‑08 مغادرة/إزالة عضو
- **الفاعلون:** الطالب نفسه / القائد / الإداري.
- **المسارات:** `POST /api/housing-groups/mine/leave` — `POST /api/housing-groups/mine/members/{studentId}/remove` (القائد) — `POST /api/housing-groups/{id}/members/{studentId}/remove` (الإداري).
- **ما بعد:** إن قائد ⇒ نقل القيادة أو حذف الغروب؛ إن عادي من `Locked` ⇒ عودة `Open`؛ مزامنة حالة الغرفة إن مسكَّن؛ إشعار المتبقّين ومن أصبح قائدًا.

### UC‑09 عرض الغرف المرشّحة للتخصيص
- **الفاعل:** الإداري.
- **المسار:** `GET /api/allocations/candidate-rooms?housingRequestId=` أو `?housingGroupId=` ← قائمة كل الغرف المصفّاة (تطابق الجنس + حالة + سعة كافية) مرتّبة بالمبنى/الطابق/الرقم.

### UC‑10 تخصيص غرفة
- **الفاعل:** الإداري.
- **شرط مسبق:** (فردي) الطلب `Accepted` وليس في غروب ولا تخصيص له / (غروب) كل الأعضاء `Accepted` ولا تخصيص للغروب.
- **المسار:** `POST /api/allocations` بـ `{HousingRequestId? , HousingGroupId?, RoomId}` ← إعادة التحقق الكامل ← إنشاء `Allocation` ← تحديث حالة الغرفة ← (غروب) `Allocated` + `AllocatedAt` ← إشعار الجميع.

### UC‑11 نقل / إخلاء / إزالة عضو بعد التخصيص
- **الفاعل:** الإداري.
- **المسارات:** `POST /api/allocations/{id}/transfer` — `/{id}/vacate` — `/{id}/members/{studentId}/remove` — والنسخ مركزية الطالب `/students/{studentId}/vacate` و`/students/{studentId}/transfer`.
- **ما بعد:** حالة الغرفتين مُعاد حسابها، `VacatedAt` مختوم عند الإخلاء، إشعارات للمتأثرين. (نقل طالب مجمَّع وحده ⇒ تخصيص فردي جديد بمعرّف جديد.)

### UC‑12 إخلاء مبنى (نهاية العام)
- **الفاعل:** الإداري.
- **المسار:** `POST /api/buildings/{id}/evacuation/announce` (إشعار السكّان، بلا كتابة) ← لاحقًا `POST /api/buildings/{id}/evacuation/execute` (ختم `VacatedAt` للجميع + إرجاع الغرف `Available` + إشعار الإتمام + ملخّص `VacatedAllocationsCount` / `NotifiedStudentIds`).

### UC‑13 دفع رسوم السكن
- **الفاعل:** الطالب.
- **شرط مسبق:** طلبه `Accepted` وغير مدفوع؛ `HousingFeeAmount > 0`؛ رصيد محفظة كافٍ.
- **المسار:** `POST /api/housing-requests/{id}/pay` ← خصم من المحفظة في AuthService ← عند 200: `IsPaid`/`PaidAt` + إشعار إتمام.
- **النتائج:** 200 نجاح / 402 رصيد غير كافٍ / 409 مدفوع مسبقًا أو رسم غير مضبوط / 400 غير مقبول / 403 ليس المالك / 502 تعذّر البوابة.

### UC‑14 التذكير الآلي بالدفع
- **الفاعل:** النظام (`PaymentReminderJob`).
- **المسار:** كل 24 ساعة ← جلب الطلبات `Accepted` + غير مدفوعة + `!ReminderSent` المستحقّة ضمن `ReminderDaysBefore` (والمتأخرة) ← إشعار «تذكير» + ضبط `ReminderSent`.

### UC‑15 سجل تسكين طالب / إعدادات الرسوم
- `GET /api/allocations/students/{studentId}/history` (إداري) — كل تخصيصات الطالب النشطة والسابقة، الأحدث أولًا.
- `GET` / `PUT /api/housing-requests/settings` (إداري) — قراءة/تعديل مهلة الدفع والتذكير والرسم.

## 7. الأمان والصلاحيات

- كل نقاط النهاية تتطلّب `Authorization: Bearer <JWT>` (تحقّق محلي RS256).
- `StudentId` **لا يُقبل أبدًا من العميل** — يُشتقّ من مطالبة `sub` في الرمز.
- تقسيم صارم: مسارات `/mine/...` للطالب مقيّدة بملكيّته (تحقّق `request.StudentId == sub`)؛ مسارات الإدارة بـ `[Authorize(Roles = "admin,super_admin")]`.
- نقطة الحذف الوحيدة المشتركة بين الدورين (`DELETE /api/housing-requests/{id}`) تفحص الملكيّة يدويًا لغير الإداري.
- **ملاحظة اتساق:** HousingService يستخدم نص الدور `"student"` (بعد تغيير في AuthService)، بينما بعض الخدمات الأخرى ما تزال تتحقّق من `"user"` — فرق مصطلح موثَّق، خارج نطاق هذه الخدمة.

## 8. قرارات تصميمية ومبرّراتها (للأطروحة)

| القرار | المبرّر |
|---|---|
| فصل `AdmissionDecision` عن `Allocation` ككيانين | «من يستحق سكنًا» و«في أي غرفة» سؤالان مختلفان بينهما فجوة زمنية (قبول موجود، لكن لا غرفة متاحة بعد). |
| فصل `HousingRequestStatus` عن `AdmissionDecisionStatus` | حالة «هل ما زال الطالب يستطيع التعديل؟» ≠ «نتيجة القبول». النتيجة تعيش حصريًا في `AdmissionDecision`، فلا تكرار ولا تضارب. |
| نموذج حالة الطلب المبسّط (`Submitted`/`NeedsRevision`/`Locked`) | حُذفت `Draft` (لا حفظ جزئي) و`UnderReview` (لا تحتاج حالة مستقلّة عن `Submitted`). |
| `Gender` مُصرّح ذاتيًا في `HousingRequest` | قاعدة تطابق جنس الغروب تحتاج جنس كل طالب محليًا، وعقد بحث المستخدمين في AuthService لا يُعيد الجنس. سابقة: أي بيانات لازمة لقاعدة صلبة تُصرّح ذاتيًا في الطلب بدل النداء الخارجي. |
| الإشغال محسوب حيًّا من `Allocations` لا من عمود مخزَّن | مصدر حقيقة واحد؛ تفادي تضارب عمود `CurrentOccupancy` مع الواقع. |
| الإخلاء يختم `VacatedAt` ولا يحذف | حفظ السجل التاريخي (من سكن أين ومتى)، اتساقًا مع فلسفة «لا حذف» للكيانات الفيزيائية. |
| `Governorate` جدول لا Enum | التوسّع لمحافظات جديدة بلا إعادة نشر. |
| `HousingCycle` مبدّل حرّ لا آلة حالة | حاجة إعادة فتح الدورة لملء أماكن غير مثبَّتة. |
| نقطة تخصيص واحدة، لا خوارزمية ترشيح | اتساق مع فلسفة «السيطرة الإدارية اليدوية» (مراجعة يدوية، قبول يدوي، إخلاء يدوي). |
| روتين إزالة عضو مشترك واحد | كل مسارات المغادرة (5 مسارات) تُبقي الغرفة/التخصيص متزامنين عبر تنفيذ واحد، فلا تتفرّع نسختان قد تختلفان. |
| المهلة تُختم عند القبول لا عند الإنشاء | خلاف مقترح فريق الفريق الأولي — وإلا لتلقّى طلاب مرفوضون/غير مراجَعين تذكيرات «ادفع الآن». |
| الجدولة داخلية (`BackgroundService`) فقط هذه المرحلة | كافية؛ ومعزولة في `IPaymentReminderService.RunAsync()` كي تُضاف لاحقًا نقطة «نفّذ الآن» + Cron خارجي إن لزم. |

## 9. القيود والأعمال المستقبلية

- **تسابق دفع ضيّق:** حارس الدفع المزدوج هو فحص `IsPaid` فقط؛ نداءان متزامنان قد يخصمان مرّتين نظريًا قبل الحفظ.
- **سجل عضوية الغروب:** لا يوجد جدول تاريخ عضوية؛ إذا سكن طالب عبر غروب ثم غادره، يصبح ذلك السكن غير قابل للتتبّع من نقطة سجل التسكين (تُحلّ عضوية الغروب من `Members` الحالية فقط).
- **حالة الغروب بعد الإخلاء:** تبقى `Allocated` (لا يوجد انتقال «الغروب انتهى» مُنمذَج بعد).
- **مضيف مجاني ينام عند الخمول:** قد تُفوَّت دقّات `PaymentReminderJob`؛ الحل الجاهز: نقطة «نفّذ الآن» + Cron خارجي.
- **ترشيح ذكي للغرف (v2 محتمَل):** ترجيح السكن السابق، الغرف المهيّأة لذوي الاحتياجات، مطابقة حجم الغروب.
