# منصة إدارة شؤون المدينة الجامعية — نظرة عامة على النظام

> **المشروع:** منصة إدارة شؤون المدينة الجامعية — جامعة حلب، كلية الهندسة المعلوماتية.
> **هذا المستند:** يقدّم الصورة الكلية للمعمارية والتقنيات المشتركة، ويُقرأ قبل مستندات الخدمات المفردة.

---

## 1. الغرض من النظام

المنصة نظام معلوماتي متكامل لإدارة العمليات اليومية للمدينة الجامعية (السكن الجامعي)، ويغطي:

| المجال | الخدمة المسؤولة |
|---|---|
| إدارة المباني والغرف وطلبات التسكين والغروبات والقبول والتخصيص والإخلاء والدفع | **HousingService** |
| استقبال شكاوى ومقترحات الطلاب والرد عليها | **FeedbackService** |
| نشر الإعلانات الموجّهة للطلاب (لافتات / إشعارات) | **AdvertisingService** |
| بناء الإشعارات وإرسالها إلى تطبيق الجوال (Push) وصندوق الوارد داخل التطبيق | **NotificationService** |
| المصادقة وإدارة المستخدمين والأدوار والمحفظة المالية | **AuthService** *(خدمة خارجية مبنيّة بـ Node.js، خارج نطاق هذا المستودع)* |
| نقطة دخول موحّدة وتوجيه الطلبات | **Gateway** |
| مكتبة الشيفرة المشتركة بين الخدمات | **SharedKernel** |

---

## 2. النمط المعماري

النظام مبني على نمط **الخدمات المصغّرة (Microservices)** مع الخصائص التالية:

- **قاعدة بيانات مستقلة لكل خدمة (Database per Service):** لكل خدمة قاعدة بيانات SQL Server خاصة بها (`HousingServiceDb`، `FeedbackServiceDb`، `AdvertisingServiceDb`، `NotificationServiceDb`)، ولا تصل أي خدمة إلى جداول خدمة أخرى مباشرةً. التكامل يتم عبر HTTP فقط.
- **بوابة API واحدة (API Gateway):** جميع الطلبات من تطبيقات العملاء (لوحة تحكم الويب + تطبيق الجوال) تمرّ عبر خدمة **Gateway** المبنيّة على مكتبة **Ocelot**، التي توجّه كل مسار إلى الخدمة الخلفية المناسبة دون تعديل المسار — مع تجميعة واحدة (`GET /api/dashboard`) تدمج ردَّي خدمتين للوحة الإدارة.
- **مصادقة لا‑مركزية قائمة على JWT:** خدمة AuthService وحدها تُصدر رموز الوصول (Access Tokens) موقّعة بخوارزمية **RS256**. كل خدمة تتحقق من الرمز **محليًا** مقابل المفتاح العام لـ AuthService، دون أي نداء شبكي لكل طلب.
- **تواصل بين الخدمات عبر HTTP + مفتاح داخلي:** النداءات من خدمة إلى أخرى (إرسال إشعار، البحث عن أسماء المستخدمين، خصم من المحفظة، جلب رموز FCM) محميّة بترويسة سرّ مشترك (`X-Service-Key` أو `X-Internal-Api-Key`) وليست برمز مستخدم.
- **تقنية موحّدة:** جميع الخدمات في هذا المستودع مبنيّة بـ **ASP.NET Core (.NET 9)** و **Entity Framework Core** ونمط **Controller / Service / Repository** مع حقن الاعتماديات (Dependency Injection).

## 3. المكوّنات المشتركة (SharedKernel)

مكتبة صنفيّة (Class Library) يعتمدها كل مشروع خدمة، وتوفّر:

| المكوّن | الوظيفة |
|---|---|
| `AddSharedJwtAuthentication` | إعداد التحقق من JWT محليًا مقابل المفتاح العام RS256 (بدون التحقق من المُصدِر/الجمهور، مع التحقق من صلاحية المدّة). أسماء المطالبات الأصلية محفوظة (`sub`، `role`، `email`). |
| `ClaimsPrincipalExtensions` | دوال مساعدة لقراءة `sub` (معرّف المستخدم) و`role` و`email` من الرمز. |
| `RequireServiceKeyAttribute` | سِمة (Attribute) تحمي نقاط النهاية «من خدمة إلى خدمة» بالتحقق من ترويسة `X-Service-Key` مقابل سرّ مشترك، مع مقارنة زمن‑ثابت (constant‑time) لمنع هجمات التوقيت. |
| `INotificationPublisher` | الواجهة العامّة لإرسال إشعار من أي خدمة (`NotifyUserAsync` / `NotifyUsersAsync` / `NotifyRoleAsync` / `BroadcastAsync`). **لا ترمي استثناءً أبدًا** — فشل الإشعار يُسجَّل ويُبتلع، فلا يُعطِّل عملية الطرف المستدعي. |
| `IUserLookupService` | بحث دفعي عن أسماء/أدوار المستخدمين مقابل دليل AuthServiceالداخلي (`POST /api/internal/users/lookup`)، بدفعات حتى 200 معرّفًا. لا ترمي استثناءً؛ نقص النتائج يعني «الاسم غير معروف». |
| `IImageUploader` (`CloudinaryImageUploader`) | رفع/حذف الصور على **Cloudinary**؛ تُعاد روابط `https` مطلقة. تُحلّ بيانات الاعتماد كسلاً (عند أول استخدام) كي تُقلِع الخدمة قبل توفير المفاتيح. |

**فائدة تصميمية للأطروحة:** جميع نقاط التكامل الخارجية (الإشعارات، بحث المستخدمين) مصمّمة وفق مبدأ **الفشل الآمن (fail‑safe / never‑throws)**؛ فتعطُّل NotificationService أو AuthService لا يُسقِط العمليات الأساسية (إنشاء طلب تسكين، نشر إعلان...).

## 4. الأدوار والصلاحيات

الأدوار تأتي ضمن مطالبة `role` في رمز JWT الصادر عن AuthService:

| الدور | الوصف |
|---|---|
| `student` | الطالب المستفيد من الخدمات (في HousingService تحديدًا يُستخدم النص `"student"`). |
| `admin` | موظّف إداري في المدينة الجامعية. |
| `super_admin` | مدير أعلى صلاحية؛ يُعامَل معاملة `admin` في كل الخدمات. |

- عمليات الإدارة (المراجعة، القرارات، التخصيص، الإخلاء، نشر الإعلانات، تأليف الإشعارات) محصورة بـ `admin` / `super_admin`.
- عمليات الطالب (تقديم طلب، إنشاء غروب، شكوى، قراءة صندوق الوارد، الدفع) محصورة بالطالب ومقيّدة بملكيّته لبياناته.
- قراءات مرجعية عامّة (الإعلانات، دورات التسكين، المحافظات، قائمة المباني المختصرة) متاحة لأي مستخدم مُصادَق (وبعضها بلا مصادقة في AdvertisingService).

## 5. النشر (Deployment)

- كل خدمة لها `Dockerfile` خاص، ويجمعها ملف `docker-compose.yml` مع حاوية SQL Server واحدة وبوابة واحدة على شبكة `university-city`.
- تُطبَّق ترحيلات قاعدة البيانات (EF Core Migrations) تلقائيًا عند إقلاع كل خدمة (`Database.MigrateAsync()` في `Program.cs`).
- توثيق الـ API متاح دومًا عبر **Swagger/OpenAPI**، وتُجمَّع وثائق كل الخدمات في واجهة Swagger موحّدة على البوابة.
- الإعدادات تُقرأ بنمط **«متغيّر البيئة أولًا ثم ملف الإعداد»** في كل الخدمات (اتساق تشغيلي بين بيئات التطوير والحاويات والإنتاج).
